# 采用与升级

<!-- LH-ADOPT-01 -->
从用户指定的目标开始检查仓库边界、已有规则与未提交修改。单仓以业务根为目标，多仓以能够覆盖关联仓库的共同目录为目标，该目录可以没有 Git。需要判定时读[目标形态](target-topology.md)。同时盘点既有规则、架构文件、规范与示例、业务记忆、原始参考、私有资料和项目服务能力，按[采用交付与验收](../assets/skills/lumine-knowledge/references/delivery.md)安排去向；目录存在不代表内容已归位。

<!-- LH-ADOPT-02 -->
先确定语言和选中的宿主 Adapter，再生成具体迁移提案。确认实际执行安装工具的 Node 为 22.x（22.18.0 及以上）或 24.x LTS（24.11.0 及以上），推荐 24 LTS。Node 18、20、其他主版本及预发布版本不在支持范围。版本不支持时，报告当前版本、支持范围和下一步，在任何工程写入前停止；不自动安装或切换 Node，不改业务 `package.json`、`.nvmrc`、依赖或用户环境配置。终端与宿主 Hook 的环境可能不同，安装工具通过不等于 Hook 已验证。使用分发 Skill 中的工具：

```bash
node scripts/harness-manager.mjs inspect <target-root>
node scripts/harness-manager.mjs proposal <target-root> --locale zh-CN --adapters <list-or-none> --output <proposal.json>
node scripts/harness-manager.mjs adopt --proposal <proposal.json>
```

已有项目使用 `upgrade --plan <target-root> --locale zh-CN --output <proposal.json>`，再用 `upgrade --apply --proposal <proposal.json>`。路径含空格时正确引用；不要把命令中的占位符当实际目标。

<!-- LH-ADOPT-03 -->
提案列出精确写入、保留、冲突、备份、语言、来源版本和宿主限制。按[迁移策略](migration-policy.md)保护实际内容和恢复状态。安装维护的同一具体范围已有授权时不重复询问；新范围或不可安全决定的冲突再请求用户决定。这不替代产品开发各阶段对具体成果的确认。用户级配置和外部动作遵守独立授权范围。

采用与升级将旧 AGENTS 和有效规则逐项归位到本轮 Validation：保留基础边界，技术细则迁入所属规范，独有规则先迁后删，框架维护解释和过期讨论表述删除或改写。每项核对来源、适用任务、权威正文、读取入口和处置理由；项目特殊授权保持原范围。规范索引应覆盖实际后端、前端、测试、插件、文档和操作任务，不为无关任务生成空规范；详细约束不得再次复制回根入口。

资料导航优先复用人工维护的 `docs/index.md` 或等价入口。旧 `workflow-artifacts.md` 与 `FRONTEND.md` 先盘点独有约束，归入导航、适用 Skill 或项目规范并修复活跃引用，再记录审阅退休依据。未审阅或仍有冲突时保留并报告；已审阅的退休沿用迁移提案、内容基线保护及恢复日志，不增加状态机或接口，也不因停止默认生成而直接删除人工内容。

<!-- LH-ADOPT-04 -->
采用[项目合同](harness-contract.md)，安装选定语言的四个日常 Skill、模板及 `.lumine/`，合并项目有效约束。按[阶段交接指导](../assets/skills/lumine-plan/references/stage-handoff.md)核对安装或升级后的根规则、工作流资料与日常 Skills：阶段内自主推进，跨阶段以人的明确确认为依据；旧的无条件跨阶段连续执行语句须在活跃指引中对齐，不改写历史决定或证据。业务根规则保持宿主中立，不加入宿主配置文件地图或社区 Adapter 兼容性说明；所选 Adapter 的实际配置仍单独维护。安装后由当前 Agent 接续 `lumine-knowledge` 的建库指导：理解实际能力、规划适应项目的目录，并默认深入覆盖所有主要模块；用户可以明确缩小范围或延后。Agent 读取来源、撰写正文与 Mermaid、核实跨模块关系；程序只准备、校验和保护性保存。大项目分批并保存恢复位置。首次采用默认交付项目化 Lumine 协作指南、操作与服务指南、资料角色去向和主要能力知识；业务服务按实际项目复用或生成扩展。根 AGENTS 只保留硬规则与直达链接，架构和详细工程资料进入 Wiki，不默认生成根 ARCHITECTURE。升级仅处理本次受影响的规则、指南、模块和未完成缺口，保留其他知识与用户修改，不默认重新生成全库。

<!-- LH-ADOPT-05 -->
完成后按[检查与证据](runtime-checks.md)验证分发、根解析和实际宿主状态，并检查已安装的阶段交接参考可读取、当前规则无冲突；仅保留旧项目文件不算完成工作流升级。用已有 Validation、coverage 和 task knowledge 记录内容交付、独立语义审阅、冷启动使用与实际操作证据，按采用交付清单收口，不新增 Runtime 状态机。分别报告安装完成、内容完成、实际验证、未覆盖及下一步；迁移 complete 不表示内容齐备或业务验收。需要并行时读[协作](worker-coordination.md)。

冷启动验收从根 AGENTS 出发，对实际适用的代表任务核对是否能定位并完整读取正确规范、模板和示例，识别必读门禁与授权边界；不能仅打开索引或通过链接检查就称内容验收完成。逐项对照原规则归位记录，检查有效规则未丢、重复正文已消除且优先级无分叉。`preserve` 是文件保护动作，不是对齐结果；保留待处理项明确报告，不增加用户审批阶段。

同时核对根入口能将就绪评估、grill／领域澄清、实施／恢复／验证、知识和设计任务路由到实际 Skill 文件；实施入口明确复用任务与当前有效绑定，缺失时创建或绑定，普通讨论、知识查询与独立检查不强制建任务。Run 指引须包含当前任务记录、并发保护、恢复核对和必要重新绑定，不能只列 Skill 名称或依赖宿主额外注入。
