# 产品方案

<!-- LH-SPEC-01 -->
Spec 先回答为谁解决什么问题，再说明目标、范围、场景、产品规则与验收。需求不完整时在同一份 Spec 内澄清，不创建前置草稿副本。只记录会影响产品选择的技术约束、接口行为和数据要求；详细技术实现归 Exec Plan。

<!-- LH-SPEC-02 -->
从 `docs/templates/product-spec.md` 取结构，但省略不适用部分。先写产品概览；描述用户操作、系统反馈和结果，覆盖实际适用的异常与恢复。必要时用 Mermaid 表达产品流程。复杂参数及完整日志链接到来源。读者不应先读聊天或代码才能理解目标与验收。

<!-- LH-SPEC-03 -->
文档使用稳定 `id`、`type: product-spec`、自身 `locale` 与真实 `status`；文件名按可读标题生成，允许中文和空格。身份不由文件名或标题推导。验收使用稳定 heading，如 `### AC-001：用户能够恢复原有会话`；删除的编号不复用。新需求关联新编号，修改既有要求保留编号并记录影响。

<!-- LH-SPEC-04 -->
正文只保留一套当前有效要求；旧批次和被替代结论进入明确的历史部分或既有历史文件。Plan 引用适用 AC 子集和内容基线；修改一项只复核受影响的引用。排版、标题和文件名变化不自动撤销批准。指纹用于发现变化，用户批准及适用范围另有依据。

<!-- LH-SPEC-05 -->
语义评审检查：问题与方案是否对应，正常／失败行为是否一致，非目标是否清楚，验收是否可观察，约束是否互相矛盾。用实际场景判断，不以章节齐全、字数或字段通过为质量标准。

<!-- LH-SPEC-06 -->
按 [阶段判断与交接](stage-handoff.md) 给出当前是否就绪、是否需要设计及推荐下一步。用户确认初版 Spec 后，按已确认的设计分支推进；设计确认后回到同一 Spec 补充有效决定并展示差异，再由用户确认进入 Exec Plan。跳过设计时也须确认 Spec 与进入技术规划。不要仅凭文档存在、状态字段或“下一步是否可行”的问句推定确认。
