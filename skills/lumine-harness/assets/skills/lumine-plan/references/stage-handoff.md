# 阶段判断与交接

<!-- LH-HANDOFF-01 -->
Agent 自己判断当前位置、材料是否足够及推荐下一步；用户确认跨阶段。Skill 是能力入口，同一个 `lumine-plan` 覆盖 Product Spec 和 Exec Plan，不代表两者可以自动连续生成。阶段内自主调查、修改和核实，不为每次工具调用或同一阶段的迭代增加确认。

## 按成果决定下一步

<!-- LH-HANDOFF-02 -->
| 当前成果 | Agent 应判断与准备 | 用户确认后进入 |
|---|---|---|
| 初版 Product Spec | 产品方向、范围、场景和验收是否明确；是否有影响实现的未决视觉／交互问题 | 需要设计则进入设计；不需要则进入 Exec Plan |
| 设计材料 | 展示必要 HTML 原型、说明或其他具体材料；核对正常与异常状态、产品一致性和未决取舍 | 回到同一 Product Spec 补充 |
| 补充后的 Product Spec | 将设计确定的行为、规则、场景和验收写回，链接材料并说明变化；纯呈现细节只更新引用及适用范围 | Exec Plan |
| Exec Plan | 技术方案、范围、任务、验证和恢复是否足以执行；是否覆盖适用 Spec 和设计 | Run |
| Run 及运行结果 | 按确认范围实施并验证，整理证据与剩余事项 | 验证可在 Run 中或之后进行，无需另设确认 |

设计是否必要，取决于是否还有影响用户体验和实现选择的未决呈现、交互或可行性问题。已有适用设计足够、沿用明确界面模式或不涉及界面时，可以建议跳过；不能只凭需求里有“设计”二字进入视觉设计。技术架构、数据流和实现取舍归 Exec Plan。验证无需阶段确认，不等于获得发布、破坏性操作或未授权环境访问权限。

## “可以进入下一步了吗”如何回答

<!-- LH-HANDOFF-03 -->
这是评估请求，不是批准下一阶段。按需要读取当前项目规则、适用 Skill、真实成果、任务进度和确认记录，并核对会改变结论的仓库事实；不把全部文档当固定必读清单，也不要求用户自己挑 Skill。

给出具体结论：

- 当前阶段及依据，已经完成什么，是否足以交接。
- 是否需要设计及理由；已有材料是否可以复用。
- 推荐的下一阶段和对应成果，仍需解决的实质缺口。
- 已有确认是否覆盖此次交接；需要确认时展示具体成果后提出清楚的问题。

例如：“Spec 已明确范围和验收，但目录展开与来源查看的交互尚未确定，建议先制作 HTML 原型。确认按这份 Spec 进入设计后即可开始。”不要把“下一步可行”写成已经获准执行，也不要在评估请求中顺手生成下一阶段全部材料。

## 确认、恢复与变化

<!-- LH-HANDOFF-04 -->
确认必须来自用户，针对已经展示的具体成果、适用范围和下一步。用户在明确的交接问题之后说“确认，继续”，或明确要求“按这份计划开始实现”，可以构成对应确认；脱离对象的模糊肯定、早期“把功能做完”、文件里的 `approved`、检查通过和 Agent 自评均不构成尚未发生的阶段确认。

在现有 Spec／Plan 或任务记录中简短保留确认依据、成果版本或内容基线、范围与允许的下一步；没有依据就保持未知，不补造批准。恢复时检查实际进度和语义变化，复用仍适用的确认；排版、标题、文件名变化不自动撤销确认。影响产品行为、范围、验收或重要设计选择的变化，返回对应成果，仅重新确认受影响部分；阶段内局部技术调整更新 Plan 即可。

待确认时停在交接处，不用 `continue` 或自动续跑越过。仅被要求完成当前阶段或就绪评估时，可以完成该请求，并说明后续待确认；完整任务尚未完成且下一步被阶段确认阻塞时，报告 `blocked` 及需确认的具体成果和下一步。状态、Skill 切换和 Runtime 均不能创造授权。

## 有边界的直接任务

<!-- LH-HANDOFF-05 -->
独立的只读审阅、验证、诊断，以及用户明确要求、没有新产品决策、不改变既定行为合同且无需跨任务协调的局部维护／修复，不强制补齐完整 Spec、设计和 Plan。仍需识别目标、范围及证据；文件少不是适用理由，不能借此绕过功能开发或产品变更的阶段确认。诊断发现失败不授权修复，实施授权不授权提交、推送或部署。
