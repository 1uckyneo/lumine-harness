# From investigation to a readable explanation

Use this method for initial knowledge building and later maintenance. The goal is to answer a reader's real question, not to demonstrate how many files were inspected. Examples below are fictional teaching material, not facts about the current repository.

## Prepare the input

Identify the reader, question and page responsibility. Gather relevant sections, implementations, tests, configuration, confirmed decisions, applicable full standards, affected relationships and human corrections. Reuse topic and document identities. A user's list of example menus is not a universal information architecture.

`wiki context "question" --json` can prepare relevant sections, rule references and neighbors. Follow the sources as needed. `wiki impact` takes changed repository paths (see its help) and returns candidates, not conclusions. Direct source investigation remains appropriate for a precisely located issue. An empty match is a reason to investigate, not to fabricate an answer.

## Seven steps

1. State the reader's question in one sentence; try the current entry point first.
2. Read the actual entry, central behavior, caller, tests, configuration and applicable standards. Names alone do not establish a dependency.
3. Extract conclusions and their conditions: trigger, valid states, success, rejection, failure and recovery. Keep facts, plans and inferences distinct.
4. Order the explanation so the reader can build an understanding. Introduce necessary concepts before implementation details; include history only when it explains the present.
5. Select prose, a diagram, aligned comparison or an interactive explanation according to the question. Do not add a diagram to every page.
6. Update the related set: body, summary, diagram, navigation, terms, relations and sources. Preserve human corrections, conditions, negations and exceptions.
7. Reread as a newcomer, then verify important conclusions. Feedback should identify a sentence, condition or entry point to repair. Keep internal scoring and source identifiers out of prose.

A useful explanation answers why, when, what follows, what fails and who is affected. If a key claim is unsupported, investigate further or remove it. Necessary limitations should be brief; warning labels do not replace good writing. Do not claim weaker-model or human acceptance without such testing.

## Business example: explain a handoff

Poor text: “The system has Project, Scheduling, Tasks and Testing modules. Projects manage projects; scheduling manages plans; fields projectId and taskId connect them.”

Investigated facts in this example: approved requirements are scheduled; scheduling assigns a person and dates to the same work; completed development enters testing; failures return to that task; passing tests is necessary before delivery.

Improved text:

### How a requirement reaches delivery

A project first establishes the requirement and acceptance conditions. Its owner assigns an implementer and dates, giving the team a concrete piece of work to execute. Scheduling changes the arrangement of that work; it does not create a separate task for each team.

After implementation, the developer submits the version and testing notes. Testers check the acceptance conditions. A failure returns to the original task for repair and another test. Passing establishes the conditions actually checked; release still follows the project's delivery arrangements.

A small flow diagram can show approval → scheduling → implementation → test, with a repair loop returning from test to implementation. Do not impose this example's lifecycle on a project with different behavior.

Why this is better: menus locate operations; the article explains objects and handoffs. Fields belong in the implementation detail.

## Mechanism example: explain an invariant

Poor text: “Publish reads GraphSnapshot, updates published/currentVersionID/draftVersionID. Rollback copies a draft. See s3:302 and s4:149-219.”

Investigated facts in this example: a new instance selects a published version, draft saves do not alter that snapshot, publishing makes a version selectable, and restoring history creates a draft which must still be published.

Improved text:

### Does editing a process change a running instance?

In this implementation an instance selects a published version when it starts and continues using that version. Saving a draft changes the content being prepared for the next publication, so it does not change the path of an existing instance.

Publishing makes the new version available for later instances. Restoring history first copies its content into a draft; it becomes effective only after review and publication. Historical snapshots remain intact and restoration uses the same publication checks.

The version selected by an instance and the current default published version are different things. To explain a particular run, inspect its binding rather than the editor's current draft.

Place the actual instance-start, publication and restoration snippets beneath the corresponding explanations. Use readable source titles and exact ranges, not internal identifiers. Investigate whether instance upgrades are allowed separately; version fields alone cannot prove that.

Why this is better: it answers impact, invariant and effective conditions first. It does not invent a business object such as “application” that may not exist in the project. A diagram is optional if these paragraphs explain the mechanism sufficiently.

## Standard example: preserve authority and exceptions

Original example rule: “Only the public export endpoint may export fields visible to the current user after both login and project membership checks. Administrators must never export secrets. Debug logs must not include complete exported content.”

Incorrect summary: “Login is required. Administrators can export everything. Be careful with logs.”

Improved text:

### The authorization boundary before export

The public export endpoint must verify both login and project membership before reading export data. Its result is restricted to fields visible to the current user.

Secrets are always excluded, including for administrators. Debug logs must not contain the complete export content. Use request identifiers and result status without sensitive content when diagnosing a failure.

This is a standard and must be read in full. Example code can illustrate the order but cannot relax membership, field visibility, the administrator exception prohibition, or the logging prohibition.

Why this is better: clarity preserves conditions, negation and scope. Ordinary knowledge maintenance cannot redefine a rule based on legacy code.

## Maintain the structure

Split by independent reader questions, not button counts. Explain a shared mechanism once and link from special cases. Locate a new capability before deciding to create a page. When a module retires, move useful concepts, repair incoming links and remove the obsolete material from normal reading. Give each relationship a reason: who consumes which result or depends on which condition. Reread from the original question after updating; a misleading old diagram or neighboring explanation means the update is incomplete.

Use existing update packets, groups, three-way merge and recovery. This guide adds no task or approval system.
