# 把机制解释成可阅读、可操作的内容

先决定读者需要理解什么，再选择表达。自然段适合结论、条件和理由；Mermaid 适合顺序与关系；对齐比较适合在同一维度看差别。只有改变条件、观察结果确实能帮助理解时，才使用交互解释器。不要把每篇文章做成组件展示页。

知识正文仍只有一份 Markdown。声明式块中的文字同样供查询和 Agent 阅读；阅读器负责布局、编号、代码高亮及图文联动。普通冒号、括号、行号和代码文本不属于指令。

## 基础合同

扩展只使用名称完全一致的 `lumine-view` 代码围栏，内容是 YAML。必填字段为 `version: 1`、`type`、`id`，可选 `title`。稳定 ID 使用英文字母开头的字母、数字、点、下划线或短横线；可见标题和解释遵循项目语言，内部 ID 不写入叙述。

每个块只描述一件事。未知字段、重复 ID、错误版本和不能对应的比较行均需修正，不绕过校验。未知块在浏览器保留原文，不执行 HTML 或脚本。修改后运行适用的 Wiki 检查，再实际阅读页面。

可复制的外部深链接优先指向块所在的稳定章节：在 Markdown 标题之前写 `<a id="稳定章节ID"></a>`。不要把会变化的标题或内部步骤序号当成永久引用。

## 1. 步骤与图解对应

先写 Mermaid，并在文档 `diagrams` 元数据中登记稳定 ID、标题、图注与来源。下面示例把三步说明对应到图的三个节点；图中的节点 ID 与 `nodes` 必须一致。示例是解释写法，不表示每个项目都按此流程执行。

````markdown
```mermaid
flowchart LR
  receive[收到请求] --> authorize[核对权限]
  authorize --> execute[执行业务操作]
```

```lumine-view
version: 1
type: steps
id: request-walkthrough
title: 一次请求经过哪些检查
diagram: request-path
items:
  - id: receive-request
    title: 识别请求对象
    body: 入口先检查必要参数，确定这次操作针对哪个对象。
    nodes: [receive]
  - id: authorize-operation
    title: 核对操作权限
    body: 权限检查同时考虑登录身份和对象范围；检查失败时，不进入后续业务操作。
    nodes: [authorize]
    source: authorization-source
  - id: execute-operation
    title: 执行业务操作
    body: 检查通过后才执行操作。执行是否成功，需要查看操作结果。
    nodes: [execute]
```
````

步骤显示真实顺序。读者选择“在图中查看这一步”时，高亮关联节点；文字始终完整呈现。步骤可以没有图，不为形式关联无关节点。

`items` 最多 20 项，每项必填 `id`、`title`、`body`。`body` 支持普通 Markdown，不嵌套另一段展示块。可选 `source` 必须指向本页已登记的来源。实现片段可写为该项的 `code` 对象，字段见下面代码示例。

## 2. 按相同维度比较

比较应解释差异的后果。列表示比较对象，行表示同一问题；每行 `values` 与 `columns` 一一对应。不能把两篇无关摘要放在两张卡片里，要求读者自行比对。

```lumine-view
version: 1
type: comparison
id: reading-and-observation
title: 阅读与来源检查各解决什么问题
columns:
  - id: read
    title: 阅读知识
  - id: observe
    title: 检查来源变化
rows:
  - label: 取得的内容
    values:
      - 已保存的解释、关系及来源位置。
      - 来源是否变化，以及需要进一步判断的线索。
  - label: 不能推出的结论
    values:
      - 阅读成功不证明当前源码完全未变。
      - 文件变化不证明业务行为已经改变。
```

支持最多 4 列、30 行。宽度不足时表格独立横向阅读，正文不缩小。文字检索按每一行的对象与值保留语义。

## 3. 就地解释术语

当术语不是主线、但部分读者需要了解时使用。核心概念和成立条件必须在正文直接解释，不能全部折叠。

```lumine-view
version: 1
type: term
id: generated-baseline
term: 什么是生成基线
meaning: 上一次生成并成功保存的正文，用于与当前含人工修改的正文、新候选进行三方比较。它不能由当前正文冒充。
```

## 4. 在解释之后展开代码

代码必须与上下文结论有关，语言名用于高亮，不改变代码。来源引用使用本页 `sources` 中的稳定 ID；可见名称由来源标题或路径呈现。

````markdown
```lumine-view
version: 1
type: code
id: relation-boundary
title: 为什么只检查直接相关的主题
caption: 影响分析的传播边界
language: ts
source: impact-source
collapsed: true
code: |
  const directlyAffected = new Set(reasons.keys());
  for (const edge of edges) {
    if (directlyAffected.has(edge.from)) {
      add(edge.target.split('#')[0], 'relation', `${edge.from}:${edge.kind}`);
    }
  }
```
````

`code` 内容必须保持原样。源文件与行范围在 `sources` 登记。省略片段要明确说明省略了什么，不能让概述代码看似完整实现。高亮或资源失败时显示原代码；复制得到原字符，不包含行号和高亮标签。

普通代码围栏已经支持高亮和复制，不需要为了颜色改为展示块。只有需要标题、来源或默认收起时，才使用此类型。

## 5. 补充说明

```lumine-view
version: 1
type: details
id: why-not-rewrite-all
title: 为什么变化后不直接重写全库
body: |
  同一个文件变化可能只是注释或格式调整。先核对影响，能保留仍然正确的解释和人工修订。

  如果确实改变多个模块的协作，应在同一个维护范围内同步它们的正文、图和入口。
```

折叠适用于补充推导、低频例外或更深实现；关键规则和用户必须作出的选择不放在默认隐藏处。

## 6. 专题交互解释器

解释器使用项目中的静态 HTML，内联 CSS／JavaScript；无需给业务仓库增加 TSX 编译环境。登记文件位于 Wiki 根下的 `assets/registry.json`，不能把任意 URL 写进正文。

```json
{
  "schemaVersion": 1,
  "entries": [
    {
      "id": "impact-explorer",
      "documentId": "knowledge-impact",
      "path": "影响范围解释器.html",
      "title": "改变来源后需要检查哪些知识",
      "text": "直接匹配来源、监控范围或主题范围后，再核对相邻关系中的解释。候选不表示这些解释一定需要改写。"
    }
  ]
}
```

`path` 相对 `assets/` 目录。页面只可使用本页登记的解释器，不能通过路径、符号链接或网络加载其他项目资料。登记条目的完整文字与正文解释一致，不把运行结果当作知识真源。

```lumine-view
version: 1
type: explainer
id: impact-conditions
title: 改变条件，看看哪些位置需要核查
asset: impact-explorer
text: |
  修改来源文件会首先命中直接引用该来源的说明，再提醒核对相邻主题。
  没有命中已登记范围的文件会单独列出，不能因此认定它没有知识影响。
input:
  changed: source
height: 480
```

解释器必须带完整 `text`，最多 20 个简单输入值。它在隔离 iframe 内运行，没有宿主同源权限，不访问项目凭据、业务接口、外部网络，也不能触发真实写入。不要设置 `allow-same-origin`。

解释器可接收父页面发送的 `lumine:input`，字段包括 `asset`、`input`、`locale`、`theme`；向父页面回传 `lumine:ready` 或 180–900 像素范围内的 `lumine:resize`。两者都携带登记 `asset`。父页面仅接受当前 iframe 的消息；解释器仅接受 `event.source === parent` 的消息。输入只是展示条件，不成为可执行代码或路径。

保持暖白、深色文字和少量暖色强调，使用中文可读字号。操作控件必须带标签和键盘焦点，结果区说明为什么变化。解释器异常时，文字仍能完整回答原问题。

## 从旧展示指令迁移

不再把普通冒号当指令解析。已有 `:::steps`、`:::comparison`、`:::details` 先逐项阅读，保留其独有文字：有顺序关系的转为 `steps`，有共同比较维度的转为 `comparison`，补充说明转为 `details`；不适合组件的恢复为普通段落或列表。

迁移通过已有 Wiki 更新包保存，保留正文身份、稳定章节、人工内容、来源与恢复依据。不要用全库字符串替换推断旧块结构，更不要将原文删除后凭摘要重写。转换后检查普通冒号、路径行号、中英标点、代码字符、图示与来源，并从读者入口重新阅读。
