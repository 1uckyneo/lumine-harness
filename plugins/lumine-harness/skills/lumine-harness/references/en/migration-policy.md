# Migration and recovery policy

## Scope and preconditions

Inspect tracked, staged, untracked, nested Git, and worktree state. Bind a proposal to target identity, source version, language, operations, pre/post baselines, and backups. Continue when existing authorization covers the proposal; an approval field cannot substitute for authorization. Preserve unexpected edits and conflicts and reassess the affected portion without stashing, resetting, or overwriting.

## Project content

Preserve valid safety, business, read-only, and Git constraints in concise project AGENTS. Update current Specs/Plans without rewriting history, evidence, or approval as a new state. Readable renames retain old path/section redirects; unmapped history remains readable. Permanent language changes migrate managed resources and defaults for new content, not bulk-translate human or historical documents.

Record each original rule, source/applicability, disposition (retain, move to a standard, rewrite, or remove), destination body, authority, and task-based reading route in this request's Validation. Preserve unique root-held rules and project-specific authorization before removing duplicate text. Concision must not revoke existing service or tool-install permission or spread it to other projects. Maintain technical details in their owning standard and only routing/basic boundaries in the root. Distinguish obsolete discussion wording from valid constraints before deletion. An ordinary preserve action protects a file but does not establish reconciled responsibilities, conflicts, or routing; record unresolved gaps and recovery locations.

Retain business Skills; expose only four canonical everyday Skills. Migration tools own compatibility mappings rather than filling new Skills with historical aliases. Old read records do not prove new rules were read.

## Recoverable writes

Each project follows preflight, staging, apply, verify, and completion. Preserve recovery content before writing, use atomic replacements, and log operations. Recovery entry points and logs cannot depend on the Runtime being replaced. Store backups and recovery logs in protected locations, not disposable caches. When changing Node support policy, retain previous migration tools, their recovery dependencies, and logs. A new release rejecting an older Node must not remove or interrupt the existing recovery path.

Resume only from expected old or already-applied states; any third content state is an external edit. Roll back only files still matching this migration's output to preserve later user work. Record cross-repository operations individually rather than assuming an atomic transaction. Mark migration complete only after verification.

.lumine/wiki-state/ is project knowledge, not Runtime-managed disposable content. Do not delete private material, migration backups, or unique recovery content under .lumine/local/ based on its directory name. Report conflicting runtime-root identities rather than merging writable state; compatibility entry points only forward to the confirmed new core.

## Hosts and external actions

Install selected adapters only, respecting host requirements for user configuration, project permissions, and plugin installation. Source, standalone Skill, and Plugin distribution share canonical content without host-specific rule copies. Without real Hook or read evidence, report static readiness only. Adoption does not automatically commit, publish, or change global user configuration.

## Artifact integration and retiring old entry points

The proposal identifies each existing artifact's role, current destination, preservation/migration/archive/deletion action, and reason. Product proposal goals, scope, scenarios, rules, and acceptance belong in Product Spec; technical approach, tradeoffs, execution/verification arrangements, progress, and records derived from applicable Specs/AC items in Exec Plan; stable language, lasting decisions, architecture, standards, examples, and guides in Wiki; actual results and original evidence in Validation; original reference material in references; read-only history in archives; personal and private originals in ignored local storage. Preserve valid constraints and historical evidence. Old active/done states, memory, or code inference do not become current confirmation.

Do not generate root ARCHITECTURE by default. Identify unique content and its Wiki destination, repair document/rule/other active references, and verify historical preservation and recovery before removal through an authorized proposal. Preserve and report files that cannot be integrated safely, have valid remaining references, or conflict with another session. Never delete just to match a new layout. Likewise, preserve recoverable originals, map current material, and check active entry points before retiring an old documentation layer; avoid permanent double maintenance.

Renames preserve stable identities and necessary aliases, with link and cross-platform name checks. Upgrades review only affected content, do not reopen other business requirements, and preserve Specs, tasks, and untracked material added by concurrent sessions.
