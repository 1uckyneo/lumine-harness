# 工作资料如何分工

Lumine 让目标、技术方案、已有知识和实际证据各有一处可信记录。用户提出自然语言目标，Agent 判断当前阶段、所需能力与下一步；用户确认阶段交接，不需要手动选择 Skill。

| 资料 | 回答的问题 | 维护方式 |
| --- | --- | --- |
| Product Spec | 为谁解决什么问题，行为与范围是什么，怎样验收？ | 原位维护产品方案的目标、范围、场景、业务规则及稳定验收标准。 |
| Exec Plan | 这次怎样实现，现在到哪里，下一步是什么？ | 承接适用 Spec／AC，维护技术方案、取舍、执行与验证安排、进度和实施记录；链接详细验证证据。 |
| Repo Wiki | 已有机制、确认的领域语言与长期决定、工程规范和使用方法是什么？ | 现状、规范、示例、指南分清效力和实现状态；每项一份正文，引用来源与有效决定。 |
| Validation | 实际做了什么，结果是什么，能证明到哪一步？ | 保留日期、操作、代码／环境适用范围与原始证据，不改写历史结论。 |

产品工作按 Spec →（必要设计 → 补充 Spec）→ Exec Plan → Run 推进，各阶段交接需人的明确确认；无需设计时省略设计及回写分支。Agent 先核对目标、材料、仓库事实和适用 Skill，再给出下一步判断，阶段内自主。只讨论 Spec 不产生技术 Plan；Run 中或之后的验证不另设确认。局部明确修复、规则维护和仅验证按自身范围处理，不强制补全产品流程。详细判断、确认依据与恢复方式见[阶段交接](../skills/lumine-harness/assets/skills/lumine-plan/references/stage-handoff.md)，本页只维护资料职责。

## 日常能力

- `lumine-plan`：产品和技术规划及语义审阅。
- `lumine-run`：实施、恢复、验证和诊断；只验证不自动修复。
- `lumine-knowledge`：定位、检索和维护知识。
- `lumine-design`：具体视觉和交互选择。

`./.lumine/cli` 提供确定性检查，不能替代上述语义判断。诊断收口可以报告失败，不代表需要自动修复。

## 关联、语言与历史

文档、验收、章节和图使用稳定身份；中文／英文可读文件名与身份分开。Spec 的一项变化只复核引用该项的 Plan，内容指纹不代表批准。历史证据继续适用于原基线。

项目语言控制新内容默认值，已有文档保持自己的语言。先呈现当前结论，再给技术细节与历史；省略不适用章节，完整日志通过链接访问。设计材料按需要选择，不复制固定附件套件。

## 知识与实现

Plan 中的拟议方案不能提前变成 Wiki 实现事实。确认的领域语言和长期决定可在相关 Wiki 主题保存，明确确认依据、上下文和未实施边界。AGENTS 通过明确规范入口指定规范附件，编辑前按任务完整读取；根入口不复制技术细则。规范、讲解示例与实现事实效力不同，普通知识同步不得放宽规则。细则直接更新所属规范，适用范围或路由变化才更新根入口；源码、实测与部署范围分别说明。

知识由 Agent 理解来源后维护：目录按项目实际能力组织，首次默认覆盖主要模块；任务中自主选择 Wiki、源码或组合，不强制查询。核实缺口、过期或矛盾后，把授权范围内的可复用结论写回受影响主题；明确只读时只报告。工具负责搜索、变化线索和保护性保存，不能代替语义理解。

收尾使用 done、continue、blocked 三种控制状态，具体阻塞原因与下一步另行说明。状态不增加授权，讨论、诊断、实施、运行验证和部署按当前请求分别判断。
