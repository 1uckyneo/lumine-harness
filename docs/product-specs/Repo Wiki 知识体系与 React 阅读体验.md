# Repo Wiki 知识体系与 React 阅读体验

## 1. 产品目标与当前判断

让 Repo Wiki 成为人和 Agent 都愿意使用、能够核实、越用越有价值的项目知识库。人通过它理解系统、定位机制和查证来源；Agent 按任务自主调查，将核实后的稳定认识沉淀下来，帮助下一次工作。

本次改造同时解决知识体系与阅读体验。React＋TypeScript 已由用户确定；阅读器采用组件化实现。需要跨组件共享复杂交互状态时，优先评估 Zustand，不因为它流行就要求所有状态进入同一个仓库。技术选择不能代替内容质量、信息组织和使用效果的验收。

本文是本轮改造的产品方案，不代表 Runtime、知识内容或 React 阅读器已经改造完成，也不承接此前任务的实施授权。用户在看到初版方案及设计交接问题后，明确委托 Agent 自定简洁、易读的设计并继续产出 Exec Plan；实施仍以具体计划的交接规则判断。

### 现有 Repo Wiki 是否已经是 LLM Wiki

**是，核心方式成立；但尚不能据此认定产品已经成熟。** 当前已有持久 Markdown、项目知识地图、稳定章节、来源与图解、按需检索、Agent 撰写和保护性保存。此前新上下文调查也实际复用了知识，并暴露、修订和再次复查了缺口。它已经超出一次生成的静态说明书。

“成熟”在本方案中不是认证或行业统一等级，而是可观察的工作效果：主要问题解释得清楚，重要结论有依据，陌生 Agent 能合理利用，错误能够被纠正，新知识能够再次复用，普通读者无需理解维护协议便能阅读。

| 维度 | 已有基础 | 当前判断与本次重点 |
|---|---|---|
| 项目知识组织 | 自适应目录、主题问题、章节、关系和稳定身份 | 目录齐全不等于每个问题都解释充分；补强阅读路径、跨模块机制与章节层面的回答依据 |
| 内容可信度 | 来源快照、作者／独立审阅、推断及运行限制 | 保留这些能力；让读者清楚知道结论适用范围，不能用文件未变或一张审阅绿标代表所有解释正确 |
| Agent 使用 | 可选择 Wiki、源码或组合；存在新上下文使用证据 | 证明了可行性，尚未证明多轮日常任务稳定获益；增加可复用任务样本和明确的未覆盖情况 |
| 持续维护 | 来源扫描、候选、三方比较、变更组与恢复 | 工具保护较完整；继续验证发现、理解、修订、核实和再次利用是否连成日常闭环 |
| 同步与维护信号 | 任务可以声明知识同步，扫描能列出未精确引用文件 | 引用存在不证明本次变化已被解释；未精确引用也不一定是知识缺口，需补可复核的处置依据与主题归类 |
| 人类阅读 | 知识树、卡片、正文、图解与源码摘录可用 | 阅读、查证和维护信息混排；需要重组，而不只是调整颜色和更换框架 |

基线来自当前源码及[上一轮交付记录](../validation/lumine-agentic-wiki/2026-09-29/交付验收.md)。历史记录中的测试、宿主和发布结论只适用于当时范围。已有新上下文对照是小样本，统计口径不同，不能推出普遍提速或 Token 节省比例。本次不以页面、图解或命令数量作为成熟度指标。

## 3. 范围与成功标准

本方案包含两个改造交付对象：Lumine Harness 源仓，以及用户本轮明确指定的 `ai-conv-plus-workspace` 多仓项目父仓。两者都需要落地改进并分别验收。项目名称在本地计划中用于识别交付对象，不作为阅读器自动推断项目名的规则。

| 交付对象 | 改造范围 |
|---|---|
| Lumine Harness 源仓 | 规范 Skills、知识 Runtime、React 阅读器、必要模板与说明、构建分发，以及源仓自用知识内容 |
| `ai-conv-plus-workspace` 父仓 | 同步新版 Runtime、四个共享 Skills 和阅读器；按需要对齐项目配置、入口规则及任务知识同步；复核和改进自身 Wiki 的目录、经核实的薄弱主题、来源与持久维护状态 |

通用实现由 Lumine 规范源构建和分发，当前父仓采用同一套成果，不维护分叉的阅读器或 Runtime。项目专有规则、人工内容、活跃任务进度、有效候选和历史证据保留。两个知识根继续独立，业务项目知识库不混入 Lumine 源仓内部知识；产品操作说明也不能挤占业务项目的主阅读路径。

业务子仓仅用于读取和核实。需要验证来源演进或写入失败时，使用既有版本变化或隔离样例，不修改业务实现来制造验收条件。

| 本次改进 | 已有能力的处理 |
|---|---|
| 明确知识组织与内容质量要求，修订暴露出的具体薄弱主题 | 复用现有正文、目录和身份，不重新生成全库、不推翻已经核实的内容 |
| 完善任务反哺、冲突解释和跨会话使用方法 | 复用四个 Skills、现有工作包与保护性更新，不新增固定阶段或第五个日常 Skill |
| 区分面向人的查找体验和面向 Agent 的上下文预算 | 复用来源与引用模型；必要接口扩展服务实际行为，不以新增主命令为目标 |
| React＋TypeScript 阅读器及信息层级重组 | 保留只读、本地、自包含、文本真源、离线与双语合同 |
| 补齐内容、使用闭环和阅读验收 | 结构检查、语义核实、真实宿主、使用效果与人类接受分别报告 |

成功意味着读者能够解释机制、找到修改影响和证据；新 Agent 能选择合适路径并纠正过期认识；知识修订能够被后续任务复用。仅仅“显示更好看”“有 React”“覆盖全部目录”均不构成整体成功。

阅读器面向桌面使用。窄屏和移动设备的阅读、导航及操作不在支持与交付目标内，不以响应式抽屉或移动布局作为必备能力；桌面浏览器 200% 缩放仍需可读与可操作。

本次不建设浏览器内聊天、在线编辑、任务管理、协作权限或云发布系统；不引入向量数据库或嵌入服务，优先改进现有文本检索与知识组织；不新增常驻模型、图片知识流水线或全库上下文注入。无需为采用阅读器而更换业务前端技术栈。具体组件、状态结构、依赖版本、构建方式和实施顺序由后续 Exec Plan 维护。

## 4. 知识应如何建立、使用与积累

### 4.1 从工程问题组织知识

项目知识地图继续是导航层级的唯一来源。Agent 理解用途、入口、真实模块与依赖后，给主要主题确定要回答的问题及来源范围。栏目随项目而定，不为库或 CLI 制造前端、部署等空栏目。

新读者应能从系统总览进入专题机制，再进入具体约束和修改入口。已经明确目标的读者可以从搜索或直接引用跳过总览。目录、关联和正文不能变成源码目录的机械复刻。

重要知识单元围绕实际问题提供：结论与适用范围、关键调用或数据流、需要关注的异常与恢复、约束和修改影响、可执行的验证方向及来源。按主题选择内容，不给每节强制填满同一套标题；没有证据的理由保留为推断或未知。

原始 Markdown 也需要容易进入正文。页面开头只保留必要的身份、标题、语言和简短摘要等元数据，不再让数百行来源或图解声明挡在解释之前。完整来源及详细声明仍可直接定位读取，文末来源／结构化附录是一种候选；具体存储和解析方式由 Plan 比较，并验证现有身份、引用与人工差异可无损转换。不得另写一份与正文长期漂移的“精简阅读版”。

跨模块问题需要连贯解释。例如“取消请求后任务与结果如何处理”不能只分散在前端和后端各自的页面里。公共机制集中维护，模块页说明自身差异；关联应说明为何相关，而不是只有泛化的“相关页面”列表。

### 4.2 目录覆盖与内容质量分别判断

“已有页面”“主题已整理”“问题已有解释”“语义核实适用于当前版本”是不同事实。结构检查可以验证文档存在和引用有效，不能判定问题已经被正确回答。

重要主题的问题应能定位到实际页面或章节。现有主题问题、文档引用和语义审阅优先承载这些信息；只有存在明确缺口时才扩展必要字段，不为每个章节建立审批或任务状态机。

未解释的重要机制、无法确定的部署状态、缺失来源和主动延后事项应有可恢复记录，并说明影响范围。一个主题可能已能支持正常路径理解，同时仍欠缺故障处理说明；不能简单把它显示为全部完成，也不因此禁用其已有内容。

首次建库继续默认覆盖主要模块；本次对现有知识做问题驱动的复核和局部改进。篇数、图数、字数和覆盖百分比只可作为清单，不可作为质量分数。

### 4.3 Agentic Search 是自主调查

Agent 可从目录、章节检索、直接 Markdown、源码或证据开始。能力入口保持简短，不全量注入，不要求每个任务先查 Wiki，也不以查询次数评价合规。

模型根据问题选择关键词或代码符号，展开相关章节、关系与来源；回答引用知识身份并保留条件、否定和限制。多个相关结果并不等于已有完整答案。源码与知识不一致时核对当前实现；涉及运行、部署与权限的结论还需适用运行证据。

Agent 工具维持受预算控制的文本卡片，默认最多六条且不足不凑数。人类搜索则提供继续查看结果和细化条件的能力，不将“六张卡片”或“上下文预算”照搬为浏览器限制。两者共用正文、身份、来源及检索依据，但不必共用展示容量。

### 4.4 调查所得回写，防止错误反复强化

| 发现 | 当前 Agent 的责任 | 保存结果 |
|---|---|---|
| 有知识但找不到 | 核实相关内容，修正别名、主题问题或章节组织 | 引用身份保留，后续同义问题能找到 |
| 重要解释缺失 | 读来源，补足机制、边界和必要图解 | 进入原主题或有依据的新主题，不复制整篇事实 |
| 来源变了 | 判断变化是否影响解释；可能需要修订，也可能正文仍成立 | 保存适用的核实结果，不能仅重写时间戳 |
| 知识与来源或另一页矛盾 | 查证双方依据，修正已知错误，保留真实争议及限制 | 当前检索不继续把已否定结论当成无条件事实；历史依据仍可追溯 |
| 用户指出内容错误 | 把具体纠正作为待核实线索，核对来源及已有批准决策 | 不因建议来自用户或模型就自动标为源码事实 |
| 实施产生稳定机制 | 在授权范围内整理可复用结论，更新相关图解与上下游说明 | Spec／Plan 保留目标与历史，Wiki 只写实际落地状态 |
| 证据不足或修改冲突 | 保存问题、候选、来源与恢复位置 | 不强行改正文，不宣称已完成更新 |

模型负责理解、判断和撰写；程序负责变化线索、版本检查、人工保护和安全保存。单纯扫描成功、收到候选或写入成功都不等于语义正确。

Wiki 之间的互相引用不能循环制造可信度。重要解释最终能够追溯到源码、配置、有效决策或验证证据；回答自身或未经核实的另一段模型输出不能充当独立证据。无需给每个普通句子建立复杂的声明数据库，重点是影响判断的机制、约束与关系。

### 4.5 持续维护不增加固定手续

普通任务在当前授权内遇到有复用价值的认识时更新受影响知识；没有增量可以零更新。明确只读、仅查询或仅诊断时遵守当前范围，不强制写入。发现重要缺口但不在写入范围内时给出具体位置和影响；若获准登记待办，则持久保存，不依赖聊天记忆。

新增模块、删除、改名、分支变化和未提交改动均纳入已有变化检测。影响归属由 Agent 判断，未知新文件保持待分类，不能因为没有旧引用就忽略。未解决冲突和人工决定不会随清缓存消失。

维护线索按主题和变化原因组织，区分本次新增／变化、既有待核实，以及已经评估无需逐文件解释的内容。“没有精确 sources 引用”不能自动等同于“未被知识覆盖”：某文件可能已由模块级说明涵盖。Agent 的归类、延后理由和不需更新的决定应可保留，并与适用来源范围或版本关联；范围或事实变化后重新评估，不能永久屏蔽后续新增能力。正常维护不把整仓未引用文件反复当作新欠账。

语义核实可以得出“正文仍适用”，不强迫改文。新来源改变结论时，正文、卡片摘要、图解、关系和适用审阅一起检查。只更新受影响部分；相关知识同步属于当前任务时才阻塞该任务收口。无关知识欠账不阻塞普通任务。

当任务承诺知识同步时，收口要能解释本次变化影响了什么、采用了新增／修订／保留的哪种处置，以及对应知识版本和核实范围。复用当前任务记录与知识修订，不另造查询日志。“已同步”加若干存在的引用不构成充分依据；Runtime 检查关联是否完整且适用，Agent 对内容是否支持结论负责。没有知识增量时可说明原因，不机械修改文档。

没有活动 Agent 时只检测或登记；有活动 Agent 时依据任务和授权处理。阅读器不放置无法兑现的“AI 自动修复”按钮，也不假装通过刷新页面即可完成核实。

## 5. 阅读器的信息组织与场景

### 5.1 以理解、查证、维护三个目的安排信息

| 目的 | 内容 | 默认呈现 |
|---|---|---|
| 理解项目 | 项目身份、知识目录、主题问题、核心解释、图解、本页导航和必要限制 | 阅读主界面 |
| 查证结论 | 就近来源、相关机制、适用范围、来源观察及语义核实 | 短入口随内容出现；源码摘录、完整版本和核实详情按需展开 |
| 维护知识 | 覆盖缺口、候选、冲突、更新结果、失败与恢复指令 | 独立的次级“知识维护”入口，保持只读，不成为首页仪表盘 |

与当前内容直接相关的来源缺失、解释冲突或已知失效提示必须可见，不能全部藏入详情。普通正常状态不重复铺陈哈希、时间戳、审阅协议和免责声明；“最近核对时来源未变”不能简化成“已验证正确”。

发现来源变化但尚未判断语义影响时，显示简短的“来源有变化，影响待核实”及详情入口。它与“解释已失效”分别表达，不能等到已经确认错误才提示，也不能仅凭变化就宣称正文错误。

### 5.2 首次进入与继续阅读

主身份是“当前项目 · 知识库”，Lumine 作为次级产品标识。项目名称来自确认的项目信息，不用本机绝对路径、目录截断或通用口号替代。

首次从根地址进入时展示项目知识首页：已有项目简介、按知识地图组织的主要主题、明确的总览入口和搜索。总览由现有主题内容与目录配置选定，程序不猜测哪篇“最重要”，也不另行生成一份首页知识。未指定推荐入口时按原目录顺序展示。

首页不默认按字母堆满所有页面，也不把全库进度、各种文档数量与维护统计置于主要阅读入口之前。已读用户可看到“继续阅读”，但打开显式文档／章节链接时，链接优先于任何恢复记录。回到首页不被自动重定向。

知识树支持展开、当前位置和面包屑；卡片与列表服务浏览和搜索。推荐入口、摘要和分类复用知识真源及地图，不维护浏览器专有的事实副本。知识目录不固定为教程、API、前端或部署几类。

### 5.3 正文与来源

桌面默认采用项目知识树、正文、本页导航；按桌面窗口空间和浏览器缩放收起次要侧栏时，仍能访问目录和本页导航。保留阅读位置，避免为每次切换次级详情重建整页、丢失滚动或焦点。

正文起始区突出标题、简要结论及必要状态，尽快进入实际解释。复制引用保留便捷入口；复制问题、编辑指令、导出及审阅详情放入清楚命名的次级操作。普通文章不再在正文前排列四个等权按钮和整块维护说明。

来源入口靠近所支持的章节或图解。展开可见仓库身份、相对文件路径、位置、适用版本、说明及受控代码摘录；只有页面级来源时如实显示，不能伪装成精确到章节的证明。原有完整来源仍可查看，但不在侧栏一次铺开所有长路径。打开或关闭来源面板保持正文位置，键盘焦点返回触发入口。

同一内容只展示一个正文主标题。本页导航反映实际可读层级，选中章节可感知；关系用可读说明帮助继续理解，并区分机制依赖、决策依据和普通相关主题。

### 5.4 搜索与卡片

搜索面向“我想了解什么”，支持中英文、常用别名和代码符号，不包装成尚未实现的模型问答。结果优先说明主题、命中章节、必要原文及范围，打开后定位该节。保留否定、条件及限制，不因截取让摘要改变含义。

默认搜索当前项目 Wiki。Spec、Plan 和验证资料可从正文关联或次级“关联文档”入口访问；需要全体文档搜索时由用户明确切换范围，结果标明类型和目标／现状／历史身份。它们不再与 Wiki 作为等权的主导航抢占页面。

“全体文档”限定为当前项目明确登记、允许阅读的 Wiki／Spec／Plan 及适用验证记录；不能理解为递归搜索磁盘。验证资料默认通过引用访问，纳入搜索须有明确的内容范围；本地私有材料、缓存、备份、候选、原始日志和附件不自动进入全文索引。不得因为阅读器改造改变既有来源允许范围。

筛选按需展开，已生效条件明确可见且可清除；不要求读者先理解仓库枚举、维护状态和内部类型才能搜索。空结果说明“未找到相关知识”，提供修改词语、查看目录或复制调查问题的路径，不拿低相关结果填满列表。

人类结果列表支持明确的继续查看方式；能够返回多少、是否还有结果如实显示。知识卡片仍是 HTML 文本，不需要封面或缩略图。可按用户操作预览相关图解，但不在打开列表时绘制全库图。

### 5.5 图解与排版

Mermaid 图放在所解释的机制附近，标题、说明、状态和来源与正文共同呈现。保留放大、缩放、平移、适合窗口、重置、源码复制、稳定引用和文本导出。用户主动 SVG 导出由浏览器完成；图解 DOM 不成为持久知识，也不发送给模型。

阅读优先采用一致、清晰的中英文字体层级，控制正文行宽，减少小号弱色标签。原型以正文 16–18px、行高约 1.7–1.9 为起点，中文约 35–45 字一行、英文约 60–85 字符一行作为调校参考，不机械把不同语言和表格套同一尺寸。目录与有效交互文案不能依赖 10–11px 的微小字区分层级。

正文、导航、表格、代码块、引文和告警使用统一间距与色彩语义。代码和大表格局部滚动，不能拉宽整页；长标题、中文路径及中英文混排仍可辨认。主题颜色和具体组件样式通过真实长文原型评审，不把更换字体当作完成可读性改造。

### 5.6 异常、降级和恢复

| 场景 | 用户可见行为 |
|---|---|
| 尚未建库／建库部分完成 | 说明已有与缺失内容，已有正文可读；可复制给 Agent 的建库或续接指令，不宣称点击后后台模型已运行 |
| 服务断开、请求失败 | 保留已读正文及当前位置，明确失败和重试；恢复连接与来源重新核实分开表达 |
| 快速切换页面／搜索 | 迟到响应不能覆盖最新选择；加载、空态和失败都对应当前请求 |
| 深链对应内容已改名 | 通过稳定身份及已有重命名映射定位；无可靠映射时说明失效并给出可用目录，不跳转无关章节 |
| 来源仓库缺失或源码范围变化 | 正文继续可读；查证时明确不可核实／需要重新定位，不能把当前不同文件的同一行号当成原证据 |
| 单图语法错误、超大图或关联请求失败 | 局部反馈、保留文本和 Mermaid 源码，其他正文和图继续可用 |
| 剪贴板或浏览器存储不可用 | 提供可选择复制的文本；基本阅读不依赖持久存储，说明仅不能保存偏好或位置 |
| 服务更新导致旧静态资源失效 | 给出可理解的刷新恢复入口，避免空白页；尽可能保留当前稳定引用 |
| 同端口切换不同项目 | 阅读位置、目录展开和筛选按项目身份隔离，不带入另一项目内容；服务身份变化后提示重新加载 |

支持键盘完成搜索、目录、文章、来源面板和图查看器操作，焦点清楚可见；Esc 关闭浮层后返回原触发点。浏览器前进／后退、直接链接、页面刷新及桌面窗口调整保持一致的位置语义。

## 6. 与 Lumine 其他能力的关系

| 部分 | 本方案的要求 |
|---|---|
| README／ARCHITECTURE | 保留产品定位与简短地图，链接深层知识，不复制完整 Wiki |
| AGENTS／四个 Skills | 简短告知知识能力、自主调查和授权内回写；具体方法按需读取，不强制固定工具序列 |
| Product Spec／Exec Plan | Spec 维护产品要求，Plan 维护实施方案和证据；尚未实施的本方案不能写入 Wiki 现状 |
| Wiki／Validation | Wiki 总结稳定机制和限制；Validation 保存实际操作、环境和结果，不能用正文自述代替证据 |
| Runtime／阅读器 | 统一身份、来源与文本模型；程序做确定性工作，阅读器不调用模型生产知识 |
| 安装、升级与 Adapter | 所有安装方式分发同一阅读器及能力；沿用当前知识根和服务生命周期，不制造宿主专属知识副本 |

正文与 Mermaid 是唯一知识真源，卡片、目录视图和索引由它们及持久知识地图派生。`.lumine/wiki-state/` 中的基线、人工保护、有效候选、冲突和用户决定继续受保护；升级不能当作 Runtime 文件覆盖或淘汰。

浏览器依赖在 Lumine 构建时打包并带入正式分发。采用项目的使用者无需安装 React、Zustand 或前端开发依赖；本地服务遵循[整个 Lumine Harness 的已确认 Node 支持政策](Lumine%20流程与文本知识体验.md)：Node22.x ≥22.18.0、Node24.x LTS ≥24.11.0，推荐24 LTS；该基线已按[Node 执行计划](../exec-plans/active/Lumine%20Harness%20Node%20支持基线调整.md)实施，结果与剩余宿主验证边界见[实施与验收](../validation/lumine-node-runtime/2026-09-30/实施与验收.md)，不增加 SSR 或另一套应用服务。现有只读回环监听、来源路径与 Host／Origin 校验、Markdown 清理和 Mermaid 安全限制保留。冷启动阅读、查询和既有图解渲染不依赖模型、CDN 或源仓的 node_modules。

React 仅重构浏览器实现。URL／稳定引用承载可分享位置，组件局部交互保持局部，确需共享的阅读状态才评估 Zustand；本机阅读偏好不能变成第二份知识库。具体分层由 Plan 论证，不在本 Spec 固化 Store 清单。[React 官方支持在既有项目中引入组件](https://react.dev/learn/add-react-to-an-existing-project)；[Zustand 官方仓库](https://github.com/pmndrs/zustand)作为候选评估依据。

中文与英文界面都完整覆盖正常、加载、空态、失败和恢复文案。切界面语言不翻译正文、不更改项目语言、不隐藏另一语言知识。中文、英文和混合文件名、章节及图解身份继续有效。

## 7. 验收要求

验收以真实知识与任务为主，夹具补齐异常。源仓与当前多仓项目父仓分别验证，分别报告工具同步、知识改进和阅读体验结果；源仓通过不能代替父仓验收，不把任一项目的栏目或内容配额变成通用模板。执行结果单独保存在 Plan／Validation；本节只规定预期，不预填“已通过”。

### AC-001：知识组织适合项目且能回答问题

未参与建库的读者可从项目首页进入系统总览、专题机制和相关源码。抽查主要主题的正常机制、异常、修改影响和验证问题，能定位实际解释或明确缺口。新增模块能进入适当目录；不存在空造的前端、后端或部署栏目。覆盖统计不能冒充语义正确率。

### AC-002：跨模块解释有依据且不重复维护

选取至少一条跨模块链路核实入口、状态、依赖和失败边界；正文与图解一致，重要关系可回到来源。公共机制仅一处完整维护，模块页说明差异；Spec 的目标与 Wiki 现状不混淆。错误陈述被纠正后，关联卡片和其他页面不继续无条件引用旧结论。

直接打开原始 Markdown 可迅速进入主要解释，详细来源和图解声明不占据长篇前置区；正文与附录共用单一事实源，仍可定位每个重要依据。若改变存储格式，当前内容与生成基线同时转换，保留人工差异与历史定位，不能将格式转换误报为语义复核。

### AC-003：新 Agent 能自主使用知识

独立新上下文处理机制解释、局部修改定位、跨模块调查和无答案问题；可选择 Wiki、源码或组合，记录实际路径与结论依据。不得预告必须调用某命令或固定次数。验证中英文、代码标识符、同义表达、否定条件和错误前提；不把“调用了 query”当作有效使用。

### AC-004：知识增量可跨会话复用

第一次任务发现真实缺口、核对来源并撰写修订，通过既有工具保护性应用；第二个新上下文能找到并正确使用新增认识，同时保留来源限制。保留首次失败、修订与再次核实的分别记录。无关页面不被重写；没有增量和明确只读场景不被强迫写入。

承诺知识同步的任务提供变化影响、处置依据、适用知识版本和核实范围；只有旧引用存在或仅将状态改成“已同步”的样例不能被当作完成证据。内容未变但已重新核实的场景可以完成同步，不制造无意义正文修改。

### AC-005：变化检测、语义判断和安全更新各自正确

使用隔离内容验证来源变化但解释仍成立、机制实变、新增未引用文件、来源缺失、人工改文／改图、并发、拆页和中断。扫描只给变化线索；核实与正文写作由 Agent 完成。候选、未解决冲突和人工决定可恢复，不能把部分应用或结构检查成功写成全部语义完成。

包含一个“模块已解释但文件没有逐一引用”的样例和一个真正新增能力的样例：前者不被自动判成新缺口，后者不能被旧的延后或忽略决定掩盖。相关判断的范围与理由可恢复；清缓存后不会把所有已经处理的线索重新伪装成首次发现。

### AC-006：阅读首页与主路径聚焦知识

首次进入可辨认当前项目并找到总览、主题和搜索；有记录时可继续阅读，显式深链优先。主导航不等权铺陈 Wiki／Spec／Plan；默认视图不显示整块维护统计、恢复命令和版本哈希。全部既有知识仍可从目录或搜索访问，关联文档与维护信息有清楚的次级入口。

### AC-007：降噪不损失可信度

正文、图解附近能进入相关来源和限制；有影响的过期、冲突或缺失提示默认可感知。正常内容不重复展示维护协议。查证详情区分源码事实、来源观察、作者核实、独立复核和运行证据；关闭详情返回原位置。无法精确映射的来源不能伪装成精确证明。

来源变化、语义影响待判断的样例有独立且可见的提示，不被混同于已失效或已核实。普通页面刷新不能自动清除该提示或使核实时间前移。

### AC-008：人类搜索与 Agent 预算各得其所

在多于六个可靠匹配的样本中，人类可继续查看结果，Agent 默认仍得到预算内文本卡片。命中可进入正确章节，筛选可清除；无可靠结果不凑数。仅 Wiki 与显式全体文档范围可区分；非 Wiki 结果明确标出身份，拟议方案不冒充现状。

### AC-009：长文、图解与交互具备可读性

用实际中文和英文长文、长路径、代码块及宽表格，在 1440px 桌面窗口及该桌面浏览器 200% 缩放下检查阅读与操作。正文行宽与字号协调，代码块、宽表格及图解可局部滚动，长路径可辨认，页面不横向溢出。键盘可完成主要路径，浮层焦点可返回，不出现重复主标题。窄屏和移动设备使用场景不在支持与交付目标内，不另设中屏或窄屏尺寸的必测矩阵。实际读者能讲清文中的机制和限制，组件截图漂亮不能替代内容阅读验收。

### AC-010：图解完整保留且局部失败可恢复

验证架构、时序、流程、状态和 ER 的代表内容，支持定位、缩放、平移、适合窗口、重置、引用及源码复制。错误图不阻塞其他内容；默认导出 Markdown／Mermaid，主动 SVG 导出仍安全。正常知识创建、更新与查询不生成图片、预览缓存或模型图像输入。

### AC-011：导航、项目身份与服务恢复一致

验证前进／后退、刷新、重命名映射、无效章节、快速切换迟到响应、服务断开及重启、旧 chunk 失效、剪贴板和存储受限。同端口启动两个不同项目的顺序场景不混淆身份与位置。失败有准确提示与恢复入口，基本正文不会被次级功能故障整体封锁。

### AC-012：React 改造不增加采用成本或损坏资产

独立安装与 Plugin 分发使用同源构建；分别在 Node22.18.0 与 Node24 LTS、无开发依赖、无缓存、断网和无模型调用条件下阅读、搜索和浏览既有 Mermaid。当前 CLI／服务生命周期、稳定引用与中文文件名可继续使用。知识正文、基线、人工差异、候选与历史证据不因前端重构而被覆盖。

### AC-013：内容质量与长期价值如实评价

在相同代码与知识基线上保留 Wiki 辅助和源码调查的独立样本，采用一致问题、时间及读取量口径，先比较正确性、限定和来源，再记录重复探索成本。至少另有一次来源演进后的增量使用，不能用同日一次对照证明长期可靠。不可观测的 Token、宿主动作或人类接受明确标为未验证，不推算节省比例。

问题和初始判据在评分前固定，由未参与相关内容撰写的 reviewer 按问题的完整语义评审。若判据自身过窄或有误，另记修正与重评，保留原判据、首次答案及错误，不能通过缩窄问题制造通过。

### AC-014：工作流与双语体验保持一致

中英文均可完成进入知识、搜索、读图、查证、发现缺口和返回 Agent 的路径。临时界面语言不改项目默认；只读请求、无增量任务与相关知识同步分别处理。规范 Skills 保持四个，日常资料不重新引入兼容教程、强制查询或固定审批阶段。
