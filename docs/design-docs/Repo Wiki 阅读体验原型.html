一个项目根，可以协调多个仓库

Lumine 的项目根是同时容纳工程约定、任务、知识和维护状态的工作范围。它由 .lumine/root.json 标记，不要求它本身是 Git 仓库。只有一个代码仓时，项目根通常就是代码仓根；前后端分别管理 Git 时，可以把共同父目录作为项目根。

这样，知识可以解释跨仓请求链，而提交、分支和发布仍然保持各仓边界。要区分三个问题：我在哪个项目工作、我正在使用哪份运行资源、这条事实来自哪个仓库。根声明回答前两个，项目配置里的仓库登记回答第三个。

从命令或宿主事件找到正确的根

CLI 支持显式指定项目根的命令先验证指定根；宿主入口通常从事件的工作目录开始向上寻找根声明，找不到时再尝试登记的工作区根和进程工作目录。查找会跨越普通目录及嵌套 Git 根，在遇到有效标记时停止。

如果共同父目录和子目录各自已有 Harness 标记，向上查找会选择最近的标记。解析器不会猜哪一个符合人的业务意图，也不会合并两个项目。因此跨仓操作应使用已确认的共同根。

自用源仓和安装项目为什么能共用实现

普通安装把 Runtime 放在项目目录下，把 Skill 放在规范位置。源码仓自用时，根声明可以把 Runtime 指向构建产物，把 Skills 指向规范资源。项目配置、任务和会话仍归项目根所有，不搬进被分发的 Runtime。

这也解释了升级边界：更新可分发代码，不应覆盖任务和知识的持久状态。运行资源位置可以变化，项目资料的归属不随它改变。

仓库身份稳定，物理路径可以调整

每个仓库登记条目有唯一 ID 和相对项目根的路径。Wiki 来源和验证证据使用仓库 ID 与仓库内相对路径，而不是本机绝对路径。后续目录调整时，应保留 ID 并更新登记路径；改 ID 会影响所有来源、监控范围和代码基线，不能当成单纯改名。

知识正文根在一个项目中保持单一；监控范围则可以覆盖多个登记仓库。某个仓库暂时没有检出时，既有正文仍可阅读，但不能把它的源码事实显示成最新已核实。

找错位置或配置错误时怎样恢复

先确认启动位置、项目标记与登记的相对路径。来源暂时缺失时保留知识阅读，并说明无法核实；路径越界时调整登记范围，不能绕过边界读取。源码能证明解析逻辑，不能证明所有宿主总会传入预期的工作目录。
