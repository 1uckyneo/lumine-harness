## 样例 A：订阅项目成员离开

### 输入

“帮我规划订阅项目成员离开后的处理。现在把 customer 和 user 都叫账户；退款是否存在尚需核对支付代码，付款人和使用人可能不同。我已回答成员离开时保留历史数据，其他选择还没有回答。先只讨论产品，不实施。”

### 实际规划输出

目前保持产品讨论阶段。已经明确的是：成员离开后保留历史数据；付款人和使用人不能预设为同一主体。退款能力还没有核实，其他未答项继续保留为未决，不能把推荐当成已经接受。

下一轮先做三件事：

1. 找到当前 Spec、既有领域语言资料和原问题清单，先把“保留历史数据”写回同一 Spec；对原有未答题保留原编号并去重，不重新问已经回答的保留问题。
2. 调查 Customer、User、项目成员、订阅和支付之间的实际关系，以及支付代码是否具备退款、取消订阅或席位调整能力。源码只能证明现状；若与新目标不同，分开记录。当前样例未提供业务仓，以上事实均为尚需调查，不能据 Lumine 源码推断业务行为。
3. 继续询问不依赖退款调查和未决实体关系的产品选择。以下是当前问题面；实际项目应与原问题清单合并，沿用已有编号。

❓ **Q1 — 术语区分**：同意先停止用“账户”同时指代 Customer 和 User，分别称为“订阅客户”和“使用用户”，并把“付款人”作为支付场景中的独立角色吗？这里先确定称呼与区分，不预设订阅客户、付款人和使用用户必须相同；Customer 的准确业务边界待与现有资料、源码一起核对。

➡️ 推荐同意。先保留不同概念，避免“账户离开”同时被理解成成员退出、订阅取消或用户删除。

---

❓ **Q2 — 离开场景范围**：同意本次同时覆盖成员主动退出和有权限人员移除成员，并让两种离开在生效后适用相同的数据与访问规则吗？

➡️ 推荐同意。触发方式可以不同，离开后的结果应一致；具体由谁有权移除仍沿用已有规则，发现规则缺口后单独澄清。

---

❓ **Q3 — 访问停止时间**：同意离开生效后立即停止该成员访问这个项目，保留历史数据不自动保留其访问权吗？

➡️ 推荐同意。数据保留和访问资格分别定义，避免历史保留被理解成仍能进入项目。

---

❓ **Q4 — 历史可见性与归属**：同意剩余成员按项目权限查看保留的历史内容，并保留原作者署名；成员离开本身不把内容改成匿名或转成其他人的成果吗？

➡️ 推荐同意。保留来源有利于理解历史；这里是待选择的目标规则，不声称系统当前已这样实现。

---

❓ **Q5 — 再次加入**：同意同一使用用户再次加入后沿用原身份和历史署名，并按重新加入时授予的权限访问，而不自动恢复离开前的全部权限吗？

➡️ 推荐同意。历史连续性与当前权限分别处理。

---

❓ **Q6 — 结果反馈**：同意离开操作向执行者明确反馈成功或失败，并向离开成员及项目管理人员提供结果通知吗？通知渠道先复用项目已经明确的方式；渠道尚未明确则留作后续选择。

➡️ 推荐同意。离开会影响访问资格，相关人员需要知道是否已生效。

## 样例 B：任务定义变化与已批准 Plan

### 输入

### 实际规划输出与拟回写正文

本轮完成模型、相关验收和计划的一致性更新，暂不实施。新回答明确了本 Spec 所讨论任务的负责人规则，也否定了跨部门使用同一通用 task 定义的假设。仅修改 Wiki 或替换 Plan 中的词语还不够：Spec 的验收依赖该定义，需要同步核对正文含义。

先读取现有 Spec、该 Wiki 定义、Plan 的适用 AC/内容基线与批准依据，并检索其他引用。没有正文时不伪造文件名、AC 编号、旧定义或批准哈希。默认将本次新规则限定在当前 Spec 的业务上下文；其他部门只确认“含义不同”，具体名称、定义和关系尚未给出，不替它们发明词表。

**领域语言拟回写到既有 Wiki 权威专题/稳定章节：**

> **任务（当前 Spec 的业务上下文）**：该上下文中的工作单元，每项只对应一名负责人。它与其他部门称为 task 的概念不自动等价。
>
> _Avoid_：未限定上下文的“task”或“任务”被用于跨部门通用定义。

实际回写时用既有资料确定的上下文名称替换上面的描述性占位，不把该占位发布为正式术语。拆分规则属于产品行为，写入 Spec，不把词表写成产品方案。保留既有文档/章节身份、Wiki metadata 与来源；已明确的约定可以是 `current`，但不表示实现已完成。

多上下文关系拟写入既有上下文图/稳定章节：

> 当前 Spec 的任务上下文与其他部门的 task 上下文分别维护术语。当前仅明确它们的含义不同，尚未确认一一映射、同步、拆分/合并或共享身份关系；不得用同名词推导同一实体。已有部门定义保留各自范围。没有内容的部门不创建空专题；需要跨部门交互时再核对边界和转换关系。

如果旧“任务”定义已被替代，保留历史依据并链接新范围/定义，不将旧历史改写成一直如此。这里只记录已明确语言；未提供长期取舍理由与三项门槛，不创建独立 ADR。

**Spec 拟原位修订：**

> 本 Spec 的“任务”使用所链接领域语言资料中本业务上下文的定义。每项任务只对应一名负责人。多人参与的工作应拆分为多项任务，并使每项任务分别满足单一负责人规则。不同部门同名 task 的规则不自动适用于本 Spec，也不由本 Spec 反向覆盖其他部门定义。

在原受影响 AC 下更新可观察要求，沿用编号：

- 一项任务不能被赋予多个负责人；出现多人共同参与的目标工作时，结果应体现为拆分后的多项任务，而非一项任务关联多名负责人。
- 拆分后逐项检查负责人规则；新建的要求确属新增验收时才分配新编号。
- 跨部门场景用各自上下文定义判断，不以 task 同名认定合同相同。

“参与”的边界仍有一个可能改变验收的歧义：是否包含仅查看、评论或评审的人。该问题记入 Spec 未决项；推荐把承担交付工作与旁观/评论区分，但用户没有回答前，不能把推荐写成例外。没有读取现有场景前，不声称此歧义已经由当前实现解决。

> 当前概览：本轮更新领域模型、Spec 适用验收和实施计划；尚未实施。既有批准依据保留。下一步是在文档中完成旧/新定义与适用 AC 的对比，标明需要复核的范围；用户当前要求暂不实施。
>
> 验收引用：继续使用既有 Spec 身份和适用 AC 编号；受影响 AC 更新为新的正文基线，保留原基线与此次语义差异的追溯。Plan 不复制整套产品正文。
>

>

>
