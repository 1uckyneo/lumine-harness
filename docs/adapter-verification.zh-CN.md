# Adapter 高级验证

本文面向 Lumine Harness 维护者和需要审计宿主兼容性的工程师。普通使用者不需要执行完整验证；通常只需对 Agent 说：

```text
检查当前 Agent 与 Lumine Harness 是否正常连接。
```

普通用户的产品差异和一次性设置见 [不同 Agent 能用到什么程度](adapter-compatibility.zh-CN.md)。

## 三类命令分别回答什么

### Status：现在能用到什么程度

```bash
./.harness/cli adapter status current
./.harness/cli adapter status selected
```

- `current` 从真实 Adapter 会话状态识别当前产品，不让模型猜测宿主；无法识别时应返回明确的重新启动或设置步骤。
- `selected` 汇总项目选择的全部 Adapter。
- 加上 `--json` 可以读取稳定的机器字段；默认人类输出应根据环境使用自然中文或英文。

Status 综合仓库检查、一次性设置和最近的运行证据，给出用户结论。它不生成新的兼容性证据。

### Doctor：项目和设置是否准备好

```bash
./.harness/cli adapter doctor <product|selected|all>
```

Doctor 只检查可静态观察的事项，例如：

- 是否从包含 `.harness/root.json` 的工程根目录运行；
- 项目是否选择了该 Adapter；
- 项目入口、Hook 配置或 Plugin 是否存在；
- 可读取的用户级配置是否已经安装；
- 是否还有明确的一次性产品设置。

Doctor 不能证明 Agent 已读取 `AGENTS.md`、模型理解了项目规则、Hook 在真实会话中执行，或自动续跑确实发生。

### Verify：真实 Agent 实际做了什么

```bash
./.harness/cli adapter verify <product> --begin --host-version <version>
./.harness/cli adapter verify <product>
```

第一条命令创建一轮有时效的验证任务。宿主版本由产品报告时记录为产品报告值，否则明确标记为用户提供或未知。随后必须在对应真实 Agent 中，从同一个 Harness 根目录运行连接检查和安全探针。Adapter 应自动发现当前验证任务，不要求普通用户向 GUI 注入内部环境变量。第二条命令汇总这轮真实会话记录。

Verify 是维护者验收，不是日常开发的必经命令。

## 分能力记录，而不是一个“已兼容”

每个产品分别记录：

1. 项目指令是否进入上下文；
2. SessionStart 或等价入口是否执行；
3. `.agents/skills` 是否能被发现或按真实路径读取；
4. 阶段要求 Skill 时，首次修改前能否确认它已读取；
5. 是否存在结束前门禁；
6. 是否能自动发起下一轮；
7. 六种 `WORK_STATUS` 是否正确转换；
8. 并行会话是否隔离。

一个产品可能在“项目指令”和“Skill 读取”上通过，但在“自动续跑”上不适用。Status 必须保留这种差异，不能压缩成一个含糊的绿色状态。

## 内部证据等级

机器输出使用以下证据等级：

- `official_declared`：产品官方协议声明支持；尚未观察当前安装版本。
- `repository_checked`：仓库入口、配置和受管文件符合规范。
- `runtime_observed`：真实会话中观察到对应事件或文件读取。
- `behavior_verified`：在明确的安全测试场景中，预期行为及结果均被观察到。

结果字段使用：

- `passed`：当前要求已经满足；
- `needs_setup`：需要安装、授权或开启一次设置；
- `not_tested`：尚未运行对应验证；
- `not_observable`：宿主没有提供足够的可观察信息；
- `not_applicable`：该产品不提供这项能力；
- `failed`：观察结果与协议预期不一致。

这些英文值服务于脚本和跨语言稳定性。普通兼容性页面和默认人类输出应显示自然中文，不直接暴露内部枚举。

## 一次完整验证怎么做

1. **确认范围**：记录产品名称、具体形态、版本和 Harness 根目录。
2. **开始验证**：创建一次有时效的验证任务。
3. **进入真实宿主**：从同一个 Harness 根目录开启新会话。
4. **运行安全探针**：只在 `.harness/runtime/probes/` 中创建临时材料，不修改业务源码。
5. **验证项目指令与 Skill**：使用唯一标记确认项目入口被读取，并让 Agent 读取一个真实 `.agents/skills/<name>/SKILL.md`。
6. **验证生命周期**：观察会话入口、工具事件、结束判断和必要的自动续跑。
7. **验证隔离**：在同一验证任务中运行两个并行会话，确认它们使用不同的哈希会话标识，并各自形成独立的状态 revision 和续跑请求。
8. **收集结果**：运行 Verify，并逐能力审查通过、未观察、不适用和失败项。
9. **收口记录**：删除过期或废弃的探针；按保留策略保存已审阅证据，不得把临时文件留进业务提交。

只有维护者完成的全套行为验证，才可以更新公开兼容性结论。普通用户的一次连接检查只能说明当前项目和当前会话的状态。

## 程序能证明什么，不能证明什么

程序可以较可靠地检查：

- 仓库入口、路径、受管配置和版本信息；
- 宿主实际发送给 Adapter 的生命周期事件；
- 带文件路径的工具事件是否读取了公共 Skill；
- 同一状态版本是否只请求一次续跑；
- 后续宿主事件是否表明续跑请求已送达；
- 多个会话是否使用隔离的状态。

程序不能单独证明：

- 模型是否真正理解了某条项目规则；
- 宿主没有暴露的完整上下文内容；
- 用户界面中的开关是否生效，除非产品提供可读取接口；
- 本地事件文件从未被人为修改。

因此运行记录是可复核的工程证据，不是密码学防伪证明。文档不得写成“程序保证当前 Agent 完美兼容”。

## `continue_autonomously` 与宿主续跑方式

`continue_autonomously` 是 Lumine Harness 的流程语义：当前任务仍有明确、安全且不需要新授权的下一步。

不同宿主用不同方式发起下一轮，例如返回 follow-up 消息、阻止本次停止或使用特定退出码。这些只是传输方式，不等于流程状态本身。

验证时需要确认：

- 同一条状态声明不会因 Hook 重试而重复续跑；
- Agent 完成新工作后再次声明同一状态，可以形成新的续跑请求；
- 宿主循环计数不会永久禁止后续新的状态版本；
- 达到宿主限制、连续自治上限或无进展阈值时会安全暂停；
- OpenCode 等不具备完整续跑协议的产品明确要求手动继续。

## 高级术语

- **失败时放行（fail-open）**：Hook 错误或超时后，产品仍可能继续运行。Kimi Code 等产品不能只依赖 Hook 保护高风险操作。
- **失败时暂停（fail-closed）**：门禁错误时，产品会阻止或暂停当前动作。
- **结束前门禁（Stop Gate）**：Agent 准备结束一轮时，宿主允许 Adapter 在结束前完成检查、暂停或请求继续。
- **验证任务编号（verification run ID）**：一次验证任务的内部标识。普通用户不需要读取、复制或配置它。
- **Cursor 项目信任（Workspace Trust）**：只在 Cursor 将项目置于受限状态并阻止项目 Hook 时才需要处理，不是 Lumine Harness 的通用前置条件。

## 证据与隐私

- 正常开发会话不持续记录详细验证事件；只在主动验证期间写入必要记录。
- 对外保留的 Probe 证据只保存哈希会话标识，工作目录保存为相对 Harness 根的路径；被 Git 忽略的本地运行状态可以保留宿主会话标识，以便 Adapter 继续同一会话。
- 不记录原始 Prompt、Token、凭据、Cookie、业务数据或完整工具输出。
- 事件记录使用追加式写入，并检测状态版本冲突。
- 验证记录应有过期与清理机制，不进入业务 Git 提交。

## 维护兼容性结论

产品协议或版本变化后，需要同步更新：

- Capability Manifest 中逐能力结果；
- Adapter 协议转换和测试；
- 本文的高级限制；
- 普通兼容性页面中的用户结论；
- 对应版本的 Validation 证据。

仓库测试只能证明 Lumine Harness 对当前协议假设的实现一致，不能代替真实产品验证。
